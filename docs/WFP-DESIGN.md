# Experimental WFP v2 design

## Scope and verification boundary

Version 2 adds GUI-to-service control and independent TCP upload/download budgets. GUI, shared control library and broker compile on Windows x64; their non-network fixtures pass. The kernel source has **not** been WDK-built, signed, loaded or verified. Nothing here certifies production shaping or driver safety. Windows 10 2004+ / Windows 11 x64 remains the intended driver target. UDP, quota, schedule and WFP Call mode are not implemented; unsupported GUI rules are rejected before IPC.

Both the kernel ABI and the protected JSON policy move to version 2. Configuration is 528 bytes: four u32 fields plus 32 download and 32 upload u64 rates. Status is 96 bytes. GUI/service control uses an independent strict JSON envelope carrying version 2. Update GUI, broker, policy and driver together after the old components have been safely drained/unloaded in a test VM. No mixed-version compatibility is claimed.

## Why the stream algorithm changed

`FWPS_STREAM_ACTION_DEFER` supports incoming streams only. It is not an outbound rate limiter. WFP's out-of-band contract also prohibits switching a stream between cloned asynchronous processing and inline passthrough. Therefore v2 replaces the receive-only DEFER path with **clone → absorb → pace → inject in both directions**, including an unlimited direction of a selected flow. No `FwpsStreamContinue0` calls remain in this driver.

The relevant Microsoft contracts are [stream inspection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/stream-inspection), [stream cloning](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpsclonestreamdata0), [stream injection](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpsstreaminjectasync0) and [per-NBL completion](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nc-fwpsk-fwps_inject_complete0). They informed the source; they do not replace a WDK build or Driver Verifier evidence.

## Packet ownership and pacing

- ALE filters match the exact WFP executable app ID and TCP for IPv4/IPv6. Runtime STREAM callouts remain conditional on associated flows; only new selected connections are tracked. Unrelated applications are not intercepted by these callouts.
- Each flow owns two FIFO queues and one injection-in-flight flag per direction. A placeholder reserves queue position before cloning outside the spinlock. A building item cannot be injected or freed by concurrent flow deletion; the classify path completes its cleanup. This avoids later clones overtaking earlier queued indications.
- All selected payloads are cloned with `FwpsCloneStreamData0` and absorbed with `FWP_ACTION_BLOCK`; BLOCK is part of asynchronous ownership, **not the rate-control mechanism**. The timer submits eligible queued data using `FwpsStreamInjectAsync0`. It never sleeps in classify or holds the budget spinlock while injecting.
- Every executable has separate shared upload/download budgets across all its flows. Whole indications are admitted only when sufficient credit exists; zero rate in one direction is unlimited. The burst-credit bound is the larger of 64 KiB and a quarter-second of the configured rate. Credit starts at zero. At low rates a full 64 KiB indication can wait 64 seconds at 1 KiB/s; this prototype does not split cloned indications into smaller quanta.
- Resource limits: 512 flow contexts, 4096 outstanding items, 128 outstanding items per flow, 8 MiB of accounted payload including in-flight items, 64 KiB per indication and 256 cloned NBLs per item. Metadata consumes additional bounded pool memory. Oversized indications, exhausted resources, clone/injection errors and abort flags terminate the affected tracked connection rather than switching it to unsafe inline forwarding. Flow-cap allocation failure before association increments `untracked_flows` and leaves that connection unshaped.
- One completion context owns the NBL-chain callback count plus a setup reference covering synchronous completions. Each completion frees exactly its NBL with zero free-clone flags. The last reference releases accounting, clears the direction's busy flag and releases the flow reference. Failed initiation has no callbacks and discards its chain. Zero-length FIN uses the documented NULL-chain path, which has no completion callback; its setup reference completes accounting. Abort flags are never reinjected.
- Counts are submitted payload bytes, not adapter/wire bytes or guaranteed delivery. Completion failures remain visible. Unlike the old DEFER path, incoming OOB pacing does not suppress ACK processing; sender/network buffering can outpace the bounded receive queue and trigger termination. This is a material receive-side tradeoff requiring VM evaluation before use.

## Stop, lease and unload

OOB streams cannot safely become inline when a policy is paused. DRAIN disables new associations and requests `FwpsFlowAbort0` for every tracked TCP flow, outside the spinlock with temporary references. **Pause, reapply, service stop, lost control handle and expired lease close tracked TCP connections.** Clients must reconnect after applying a policy. This is exposed in GUI action labels. [FwpsFlowAbort0](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpsflowabort0) delivers flow deletion for lifetime cleanup.

Flow deletion discards queued clones and leaves in-flight items alive until their completions return. The broker waits for flows, outstanding items and in-flight injections to all reach zero. A 30-second drain timeout retains filters and reports failure; it never force-removes a live OOB stream filter. Then it removes only product-owned management objects and verifies clear state. Runtime callouts and the injection handle stay loaded after ordinary pause/service stop. Explicit QUIESCE unregisters callouts and destroys the injection handle only with no filters/flows/items/injections; only then is DriverUnload exposed. Partial quiesce cannot rearm. Driver unload cancels the timer and flushes DPCs.

The broker renews a five-second driver lease while armed. No active policy means no heartbeat request. Runtime management objects remain non-dynamic/non-persistent: process exit must not implicitly remove filters during injection. Recovery always drains/aborts first. A crash or hung broker is not a transparent fail-open transition; the driver attempts to close tracked connections when its lease/control handle is lost. Failed aborts/completions can prevent recovery and must be investigated in the disposable VM.

## Local control boundary

`backend/control` shares strict policy/envelope types and the overlapped pipe client/server utilities. The pipe is `\\.\pipe\BandwidthLimiter.Control.v2`, local-only with `PIPE_REJECT_REMOTE_CLIENTS`. The broker holds the first/exclusive server instance for its lifetime. SYSTEM/Administrators have full access. Interactive users get only read-data/write-data/synchronize rights, **not** FILE_CREATE_PIPE_INSTANCE. See [named-pipe access rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).

The service reads the request, impersonates that pipe client only to check enabled Administrators membership, and reverts before any backend work. Failure to revert terminates the service rather than continuing with an unexpected token. Status is read-only for interactive users; Apply/Pause are rejected for non-administrators at both pipe dispatch and backend controller layers. The client requests identification-level security QoS. Before sending a policy it verifies that the pipe server PID matches the SCM-registered RUNNING `BandwidthLimiterService` PID. Service configuration and administrators remain trusted; this is not protection against a malicious local administrator.

Frames are length-prefixed strict JSON, bounded to 128 KiB. Version mismatch, duplicate/local-invalid executable paths, unsupported fields/rates and unsupported GUI features are rejected. Overlapped connect/read/write support cancellation; a frame read/write has a total two-second deadline. Backend replies are bounded to 35 seconds and the GUI waits up to 38 seconds. The client acknowledges a completely read response before server disconnect, avoiding buffered-response loss without an unbounded FlushFileBuffers. One pipe worker and bounded command/reply queues isolate stalled clients from the 500 ms broker heartbeat loop. A failed pipe worker causes controlled service drain, not a disconnected-channel busy loop.

The GUI starts only a blocked client worker. It does not probe, install, register, start, elevate or modify WFP at launch or on ordinary Save. **Check service** requests a manual snapshot. **Apply WFP limits** validates enabled saved rules and applies a transient in-memory service policy; it does not overwrite the protected policy file. **Pause WFP** drains/removes the current policy. Apply/Pause require a successful administrator-authorized connection. Startup/restart still loads the fixed administrator-owned policy file. GUI Quit stops the proxy only; the service remains independent.

## Remaining validation

The actual named-pipe authentication/ACL/cancellation/SCM identity path is compiled but not run against a live service. No real pipe exchange, driver device access, BFE mutation or TCP transfer has occurred in this session. Pure fixtures verify envelope validation, policy conversion, unauthorized dispatcher rejection, C/Rust ABI and independent shared budgets; they do not establish kernel or IPC correctness.

Required WDK/VM checks include same-direction classify ordering, clone-build versus flow deletion, FIFO and FIN/RST ordering, synchronous/multi-NBL completions, NULL FIN, failed initiation, queue overflow, large indications, memory pressure, failed flow abort, drain during clone/injection, transaction notification/rollback counts, BFE restart, lease expiry, broker crash, partial unregister, invalid/parallel IOCTLs, IPv6/VPN/offload/security-provider coexistence, actual rates and latency. Pipe tests must cover standard/UAC-filtered/elevated clients, spoofed endpoints, remote rejection, slow/truncated/oversized clients, disconnect during Apply and timeout with a late result. After a GUI timeout, check status before retrying: an authorized in-flight operation may still finish. Public distribution requires successful kernel build, code analysis, Driver Verifier, signing and reviewed installation/update handling.
