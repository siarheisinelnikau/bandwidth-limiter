# Backends without our own driver-signing account

Research date: 2026-10-31. The user does not want to enroll in the Windows Hardware Developer Program. This rules out our own release-signed kernel driver as the planned distribution path. The existing WFP v2 code remains an experimental reference, not a shipping prerequisite. This note records research and a proposed migration; no alternative backend is implemented or enabled by this change.

**2026-11-01 update:** the subsequent migration implemented the WinDivert user-mode broker, packet scheduler and GUI control path. This document remains the original comparison/proposal; see [current implementation](WINDIVERT-DESIGN.md) and [build/staging status](WINDIVERT-SETUP.md). Native runtime/traffic validation is still pending.

## Recommended candidate: unmodified official WinDivert binaries

WinDivert exposes packet capture/reinjection to a user-mode program. Its official manual states that the prebuilt drivers are already digitally signed. Reusing an accepted, unmodified upstream driver would avoid signing a new driver ourselves; our pacing implementation would run in the Rust service. This is still a kernel-driver deployment requiring administrative privileges, not a driver-free or elevation-free solution. Calling `WinDivertOpen` automatically installs/loads its driver when necessary, so even a seemingly harmless open/probe must remain an explicit deployment/runtime action. No such call was made during this research. [Official manual](https://reqrypt.org/windivert-doc.html), [versioned upstream manual](https://github.com/basil00/WinDivert/blob/v2.2.2/doc/windivert.html).

The upstream latest-release endpoint returned **v2.2.2, published 2022-09-21**, with the `WinDivert-2.2.2-A.zip` asset. This is not evidence of compatibility with every current Windows security configuration. In September 2025 the maintainer described this version as stable and the long-term supported version, with limited development activity and signing-dependent future changes. [Official release](https://github.com/basil00/WinDivert/releases/tag/v2.2.2), [maintainer statement](https://github.com/basil00/WinDivert/issues/395#issuecomment-3296393069).

WinDivert is dual-licensed under LGPLv3 or GPLv2. A proposed LGPLv3 integration would dynamically load its DLL and preserve the required notices, license texts, corresponding-source availability and library replacement rights. Distribution terms must be satisfied for the actual package; this note does not assert that the current MIT-only package already covers a future bundled dependency. Do not rebuild/patch the driver and assume its upstream signature still applies. [Upstream license](https://github.com/basil00/WinDivert/blob/v2.2.2/LICENSE).

## Comparison

| Option | Upload / download | Our hardware-program account | Main boundary |
| --- | --- | --- | --- |
| Official WinDivert DLL + signed driver | Candidate for both via user-mode packet queues | Avoided if the exact upstream signed driver is accepted and redistributed under its license | Requires administrator deployment, process/flow correlation, bounded pacing and actual Windows/security/coexistence tests |
| Windows Policy-based QoS | Built-in outgoing throttle; no equivalent arbitrary per-app incoming cap in this API | Not needed | Native upload-only fallback; detect availability and validate on supported Windows editions, domain policy and multiple flows |
| Existing explicit SOCKS5 backend | Both for connections deliberately routed through the proxy | Not needed | Already implemented; client support/configuration required; no transparent capture or UDP relay |
| Windows Packet Filter / WinpkFilter | Candidate for both using an NDIS packet framework | Potentially avoided with a licensed standard signed runtime | Vendor supplies a signed standard installer; commercial redistribution needs a license. Custom driver builds leave signing/certification to the customer |
| NetFilter SDK Standard / Full Sources | Filtering SDK, but not a solution to this signing constraint | Still needed for the supplied unsigned driver packages | Vendor explicitly says these packages contain unsigned drivers requiring the customer's EV certificate and Microsoft developer account |

Windows QoS supports outbound throttling by executable/path and TCP/UDP conditions. It should not be presented as a transparent download limiter, and an advertised per-application rate still needs multi-connection measurement on our target Windows versions. No QoS policy was created/read/changed here. [Microsoft QoS overview](https://learn.microsoft.com/en-us/windows-server/networking/technologies/qos/qos-policy-top), [New-NetQosPolicy](https://learn.microsoft.com/en-us/powershell/module/netqos/new-netqospolicy).

WinpkFilter's official download page advertises Microsoft-attested standard drivers; its licensing page separately assigns signing/certification of custom builds to the customer. Treat these as distinct products/conditions. Confirm rights to redistribute the exact standard signed package before adopting it; buying a custom build is not proof that signature work is included. [Vendor downloads](https://www.ntkernel.com/windows-packet-filter/download/), [vendor license terms](https://www.ntkernel.com/windows-packet-filter/licensing/). NetFilter SDK's current order page explicitly states that its Standard/Full Sources driver binaries are unsigned. [Vendor requirements](https://netfiltersdk.com/buy_now.html).

## Proposed WinDivert integration

The following is an engineering proposal inferred from the documented API, not a claim of implemented or measured behavior:

1. Keep the GUI and privileged broker boundary. Reuse saved application paths, directional caps and authenticated local IPC; give a replacement backend its own identity/capability/version contract. Never let a new GUI silently treat the old WFP service as a WinDivert backend. Keep the current proxy available independently.
2. Load the reviewed x64 DLL from a protected absolute deployment directory. Keep the upstream driver unchanged. An explicit setup/enable action must precede any `WinDivertOpen`; ordinary startup, Save, status checks and headless previews must not accidentally load/install a driver. Report unsupported or blocked components as unavailable.
3. Track FLOW/SOCKET events and correlate the IP/protocol/local-port/remote-port tuple to PID and executable identity. NETWORK packet metadata does **not** contain a PID. Flow events predating an open handle are unavailable; process exit/PID reuse and first-packet races require explicit handling. Compare event timestamps with process creation time, seed/reconcile read-only endpoint inventory where possible, and expose unknown/unshaped traffic rather than pretending attribution is exact. Initially limit documented support to newly observed TCP connections; UDP requires separate mapping/lifetime/fragmentation work.
4. Capture/reinject with bounded user-mode queues and independent per-executable upload/download budgets shared across flows. Preserve per-flow ordering and promptly forward unrelated or unidentified traffic. Keep TCP handshake/control handling, retransmissions, IPv6, fragments/offloads, queue overflow and cancellation explicit. Measure whether unshaped first packets or retransmissions bypass the intended aggregate budget. Do not implement the limiter as an unbounded packet queue or a fixed sleep per packet.
5. Account for packet bytes and retransmissions separately from the proxy's delivered payload counters. Incoming packet pacing still does not prevent packets physically reaching the network adapter; verify sender behavior, memory bounds and latency under fast senders/slow readers. Shutdown should stop capture, release queued packets according to a documented bounded policy and close handles; do not copy the current WFP stream-abort lifecycle without reevaluating packet ownership.
6. Add isolated attribution/pacing/queue fixtures first. Real driver loading, traffic capture and end-to-end measurements remain a later explicitly authorized VM phase. No package download, installation, signature validation, driver open or packet interception was performed for this note.

The layer/PID and queue constraints above come from the [WinDivert manual](https://reqrypt.org/windivert-doc.html), including its FLOW/SOCKET, filter-language, queue-parameter, shutdown and known-issues sections. WinDivert supplies packet transport, not a ready per-application bandwidth limiter.

## Deployment evidence required before selecting it for distribution

Inspect the exact official archive and x64 driver's hashes and signatures, verify the relevant kernel trust/catalog chain and timestamp, and test loading on a disposable updated Windows VM with the intended Secure Boot / Memory Integrity / driver-policy configuration. A valid Authenticode status alone does not establish kernel load acceptance or compatibility. Windows driver trust policy has continued to evolve; do not promise that a generic “signed driver” statement covers every build or future policy. [Microsoft Windows Driver Policy](https://support.microsoft.com/en-us/windows/hardware/drivers/the-windows-driver-policy).

One upstream October 2026 issue reports Defender quarantining the official archive; this is a user's report, not a confirmed universal detection or a vendor/Microsoft verdict. It reinforces the need to evaluate the exact artifact instead of disabling protection or assuming the entire archive is trusted because one member is signed. [Artifact-specific upstream report](https://github.com/basil00/WinDivert/issues/411). If our protected test intake blocks a binary, stop that path and obtain an upstream resolution or choose another candidate.

The next implementation milestone is a WinDivert adapter with fixture-only tests and no automatic loading. A release decision remains conditional on signed-runtime compatibility and distribution evidence. Native QoS is a useful smaller upload-only alternative; the existing SOCKS5 proxy remains the complete driver-free option for cooperative TCP clients.
